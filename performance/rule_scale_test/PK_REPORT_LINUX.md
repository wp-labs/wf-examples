# wfusion vs IBM QRadar EP — 450 规则吞吐性能报告（Linux 8 核对等口径）

> 测试日期：2026-08-17（**wfusion 0.3.1** / wp-reactor 1.0.2，P0-② content 记账）
> 对标：IBM QRadar Event Processor 认证负载（**80k EPS @ 451 条规则**）
> 场景：`wf-examples/performance/rule_scale_test`（450 条有状态规则 / 6 类事件源 / 1000 sip 键）
> **本报告为 Linux 8 核云主机复测**——8 vCPU 单进程跑 450 条有状态规则，验证规则求值
> 在低核数云主机上的能力，与 Mac 报告（16 核 M3 Max）口径分开引用。

---

## 1. 摘要

在 **Linux 8 核（AMD EPYC，KVM）** 云主机上，wfusion 单进程处理 450 条有状态规则，
**1M 稳态 EPS ≈ 110.5k**（三轮 111.4 / 111.6 / 108.6k，±1.4%），**超过 QRadar EP 认证
上限（80k）1.4×**——且是在 **8 vCPU**（vs QRadar 认证 56-80 核）上做到，核心结论与
Mac 报告一致：450 规则求值吞吐不是瓶颈。

| 结论 | 结果 |
|---|---|
| 450 规则稳态吞吐 | **~110.5k EPS**（1M，三轮 111,385 / 111,615 / 108,551，±1.4%） |
| vs QRadar EP 认证上限 | **1.4×**（80k @ 451 规则，56-80 核 + 128GB） |
| vs QRadar 物理 appliance | **5.5×**（20k @ 16-20 核） |
| 每核效率（按 8 核估算） | **~13.8k EPS/核** vs QRadar 虚拟版 ~1.0-1.4k（**高 ~10-14×**） |
| #18 门禁 | **通过**：内存驱逐 0，emitted ~6.8M（1M 事件），359/450 规则触发 |
| 内存 | **~4.9GB**（1M 平台期峰值，/proc VmRSS） |

## 2. 测试环境

| 项 | 值 |
|---|---|
| 芯片 | **AMD EPYC 9T95**（KVM 虚拟化，8 vCPU / 8 核 / 每核 1 线程，x86_64） |

| 注入 | `wfgen send` 单连接流式（CHUNK=10000），1M 事件（三轮） |
| 对照 | QRadar EP 1699（虚拟版）：56-80 核 + 128GB，认证上限 80k EPS @ 451 规则 |

---

## 3. 结果（1M 事件 × 三轮，blackhole sink）

| 轮 | EPS | RSS 峰值 | emitted | 规则触发 |
|---|---|---|---|---|
| 1 | 111,385 | 4.78GB | 6,587,233 | 358 |
| 2 | 111,615 | 4.99GB | 6,870,810 | 359 |
| 3 | 108,551 | 5.02GB | 6,877,859 | 359 |
| **均值** | **~110.5k**（±1.4%） | **~4.9GB** | **~6.8M** | **359/450** |

正确性：三轮全部驱逐 0、无 dropped_late / serialize_failed / cursor_gap，#18 门禁
通过。emitted ~6.8M（1M 事件多规则命中 ~6.8×，量级与 Mac 报告 1M→10.2-10.4M 一致；
绝对差异来自随机数据分布，非正确性问题）。

---

## 4. 对等分析（8 核 vs QRadar 56-80 核）

1. **8 核单进程 110.5k > QRadar 认证 80k**（56-80 核 + 128GB）——倍率 1.4×，硬件算力
   差距远超倍率（8 vCPU vs 56-80 核）：**规则求值吞吐本身不是墙**，与 Mac 报告结论一致；
2. **每核效率**：按 8 核满负荷估算 **~13.8k EPS/核**（未测 CPU%，见诚实边界）——vs
   QRadar 虚拟版 ~1.0-1.4k EPS/核，**高 ~10-14×**；
3. **vs Mac（156k 中位）≈ 0.71×**：450 规则是规则求值（CPU-bound）瓶颈，云主机
   8 核 + EPYC 单核弱于 M3 性能核；幅度远小于 nexmark 简单查询的 1/3——规则求值
   吃满多核，简单查询吃单核/带宽，rule_scale_test 的 CPU-bound 形态在云主机上损失更小；
   （200k 突发 0.66× → 1M 稳态 0.71×，稳态口径略优于突发。）

---

## 5. 结论

- **Linux 8 核对等口径下，450 规则稳态能力仍超 QRadar 认证上限**（8 核 vs 56-80 核），
  与 Mac 报告的架构优势一致——对外引用建议用本报告（低核数云主机，对 QRadar 最不利
  的口径）；
- **每核效率 ~13.8k vs QRadar ~1.0-1.4k**，消除核数差异后优势仍 10 倍量级；
- **RSS ~4.9GB**（1M 平台期峰值，/proc VmRSS），低于 Mac 1M 的 ~6.7GB（吞吐低 →
   窗口/输出驻留少，与 nexmark Linux 报告的 RSS-随吞吐-下降趋势一致）。

---

## 6. 诚实边界

1. **EPS 为 1M 三轮稳态**（111,385 / 111,615 / 108,551，±1.4%）；单连接流式、CHUNK=10000；
2. **RSS 为 `/proc/<pid>/status` VmRSS 平台期峰值**（Linux 回退路径；macOS 用的是
   `footprint` 的 phys_footprint，两者口径略异，跨平台对比看量级）；
3. **CPU% 未测**：每核效率按 8 核满负荷估算，未用 `wait4`/rusage 实测；
4. **QRadar 数字来源单一**（IBM 官方认证方法论），不可复现；对照含板载采集/存储等
   产品层组件（非仅规则引擎），利于 QRadar；
5. 硬件：AMD EPYC 9T95（KVM 虚拟化），8 vCPU / 8 核，30 GiB，Ubuntu 24.04.4。
