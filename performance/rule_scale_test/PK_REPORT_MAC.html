关键结论

  1. 450 规则稳态 150-162k = QRadar EP 认证上限（80k）的 ~2×，且是带窗口/实例的有状态关联规则，不是裸过滤；
  2. 窗口 1GB 是 1M 长跑的坑：conn 窗口深内容 ~2.5GB+，1GB 触发有损驱逐；4GB 后驱逐 0——窗口 cap 必须与数据量匹配（nexmark 同经验）；
  3. 供给非瓶颈：EPS 远低于引擎输入能力（nexmark q1 单规则 7.5M），450 规则求值是瓶颈；连接数/分片/instances 非杠杆；
  4. CHUNK=10000 最优：与 nexmark 100k 帧甜点不同，规则求值主导时批大小影响小。

行业定位（450 规则，单节点 M3 Max）

换算：~156k 事件/s × 450 规则 ≈ 7000 万次规则求值/s（每核 ~17-27M 次/s，均摊 ~37-60ns/规则求值，含 per-sip 实例状态与窗口维护）。

诚实边界

  1. 硬件不对等：wfusion 单进程 @ M3 Max 笔记本芯片 vs QRadar 56-80 核 + 128GB 服务器——倍率含硬件口径差异，但每核效率对比（12-27×）已消除规模因素；
  2. 键基数不对等：本场景 1000 sip 复用 vs QRadar 250k 唯一源 IP——直接对比偏保守有利于 QRadar（键基数大 → 实例状态/哈希成本更高）；
  3. EPS 口径：send 墙钟（客户端回放完成时刻）——1M 稳态三轮稳定（±8%），且注入速度 ≈ EPS（背压约束），未用预编码帧（send-arrow）做客户端成本隔离；
  4. sink 为 blackhole（discarding，对齐 Flink Nexmark 口径），落盘 file sink 慢 ~4-5%；
  5. QRadar 数字来源单一（IBM 官方认证方法论），不可复现；对照含板载采集/存储等产品层组件（非仅规则引擎），利于 QRadar。
