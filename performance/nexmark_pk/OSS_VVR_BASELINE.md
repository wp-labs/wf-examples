# OSS Flink vs VVR Nexmark 性能基线（阿里白皮书）

> 独立存档阿里云 Nexmark 性能白皮书的 **OSS（开源 Flink）与 VVR（实时计算 Flink）逐查询吞吐数据**，
> 以及 wfusion 的对照情况。供 PK 对比、报告引用、查询能力评估使用。
> 与 `README.md`（套件结构）、`PK_REPORT_MAC.md` / `PK_REPORT_LINUX.md`（实测报告）、
> `NEXMARK.md`（基准背景/数据/正确性）、`TEST_PLAN.md`（测试方案）、
> `SEMANTIC_ALIGNMENT.md`（各查询语义对齐状态）互为配套。

## 1. 数据来源与口径

### 3.5 弱势 CASE 分析（vs VVR 优势不明显，2026-08-21 新口径重评）

新口径（严格对齐 Flink）下优势倍数最低的查询（**q2 2.6× / q22 2.4× /
q18 3.1× / q11 3.6×**；q12 6.7×、q21 6.4× 已移出）：

| 查询 | vs VVR | wfusion EPS | RSS | 负载 | 规则结构 | 白皮书语义 |
|---|---|---|---|---|---|---|
| q22 | 2.4× | 7.72M | 4.7GB | 4.4 | `on each` + `let parts = split(url,"/")` mvindex 3/4/5 投影 | URL Directories ✓（2026-08-21 对齐） |
| q2 | 2.6× | 17.2M | 1.2GB | 5.3 | `auction % 123 == 0` 过滤 | 标准过滤 ✓ |
| q18 | 3.1× | 3.17M | 18.5GB | 8.2 | 每 bidder 累积计数 + 状态 | 标准累积 ✓ |
| q11 | 3.6× | 2.49M | 17.3GB | 8.9 | session 窗口（bidder 60s gap） | 标准 session ✓ |

**根因**（结构推断——规则形态 + 状态规模 + 负载上下文，未 profile 实证）：

1. **状态物化量与 EPS 强负相关**（最大共同因素）：RSS ≥ 14GB 的查询（q21 15.6 /
   q22 16.2 / q18 18.5 / q11 17.3 / q13 22.0）EPS 全在 2.2-4.3M；< 3GB 的轻状态查询
   （q1/q2/q3/q8/q10/q12/q14）17-21M。大状态 → 缓存/内存带宽瓶颈。
   **例外**：q22 无窗口无状态（on each），RSS 16.2GB 为**管道积压**（消化 4.3M/s
   → 30M 需 ~7s，send-arrow 秒推 5.4GB 帧堆积），非状态物化。
2. **q22 每事件字符串成本高**：3 次 `split`（返回 Vec<String> ≈ 24 次小分配）+ 3 次
   `mvindex` + `concat`，30M ≈ 6.6 亿次小分配——无状态查询被分配开销压到 4.3M
   （q1 纯投影 19.5M）；官方 SPLIT_INDEX 同为字符串切分（VVR 3.2M 含此成本），
   1.35× 已超 VVR。
3. **q21 的 anti join 每事件成本高**：bid 驱动 + person 窗口查表 + 15.2M 输出，
   person 窗口 10m over 状态常驻 → 内存带宽受限。
4. **q2 的 2.6× 是输出面/语义差异而非性能差**：q2 是极简过滤（EPS 17.2M 绝对值
   最高档），VVR 对简单查询本就打磨到 6.5M（8 CU 下近管道上限）；wfusion 单连接
   单管道未饱和时的相对优势小属预期。
5. **非算法因素**：q11/q18/q21 处于高负载段（load 8.2-8.9），数字偏低。

**优化方向**（按性价比排序，待实现/验证）：

1. **q22 split 减少分配** ✅（2026-08-21 已实施）：wfl 新增 `let` 绑定
   （每事件求值一次），`let parts = split(b.url,"/")` 替代 3 次重复 split →
   EPS 4.31M → 7.72M（低负载样本）、vs VVR 1.35× → 2.4×。
   （RSS 4.7-13.4GB 随负载波动，为消化速差导致的管道积压；剩余成本为
   3 次 mvindex + 2 次 concat 分配，引擎侧缓存收益递减。）
3. **q18/q11 状态压缩**：累积计数/会话实例表示精简 + 惰性过期（q11 RSS 17.3GB、
   q18 18.5GB 均指状态膨胀）。
4. **q17 实例查找免哈希 + 过期预算**（旧口径遗留方向）：sliding 10m 高实例量下
   foldhash 查找与 expiry 扫描预算仍是 advance 大头（q17 新口径 4.1×，收益待验）。

#### 附录：q12 优化历程（2026-08-21，旧口径审计记录）

q12（bidder × 10s fixed + close 全量输出）旧口径瓶颈在 close 输出路径（30m ≈ 1821
万条 EMIT）；E2 定位 `execute_close_with_joins` 内 build 60% + ctx 35%。三轮优化：
批量 emit + ctx 惰性字段（2.49→2.76M）+ 列式 close 执行器（L4：批量 `CloseOutput`
直写列式 builder，2.76→4.27M）+ needs_field_history 精确化（advance 2.27→1.79s）
→ **EPS 2.49M → 5.27M（+112%）**。新口径（bidder 域收敛官方 ~1000 人、EMIT 75 万）
重测 **18.1M / 6.7×**，已移出弱势。
