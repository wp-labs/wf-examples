## 附：q14 优化探查（2026-08-25，Mac 100M + diag 墙表）

> 背景：q14 曾误标为「Top-N」——实为 **Calculation**（`0.908*price` 过滤 + `HOUR` 分型 +
> `count_char` UDF，`on each` 无状态投影），无 stats/conv top 路径。错误标注已修正
> （`OSS_VVR_BASELINE.md` 查询注记、本文件三处 PK 结论）。

**A/B 实测（Mac 100M，同机背靠背）**：`let h = strftime(b.dateTime, "%H")` 绑定一次
（原 yield 两分支各求值一次，最多 2 次 chrono 格式化）→ EPS 6.05M vs 原版 6.14M，**±2% 噪声内
无增益**——strftime 不是热点。

**diag 墙表（q14 1m，增量口径，与更大 N 归属一致）**：

| 档 | ns/事件 | 增量 | 占全链 |
|---|---|---|---|
| floor（注入+解码） | 50.8 | — | 34% |
| rules（+规则求值） | 92.9 | +42.1 | 28.5% |
| full（+输出链） | 147.5 | +54.6 | **37.0%** |

**结论**：主墙 = **输出链**（+54.6ns，fmt detail 构建 + alert 序列化 + blackhole 写）；其次规则段
（+42.1ns，bind filter 全量求值）。q14 每命中事件（~28% bid）需构建 detail 字符串（小时分型 +
count_char），属 Flink 语义固有成本；vs VVR 1.07~1.20× 的差距主要来自此工作负载形状，非明显
可消除的热点。**候选优化（未实施）**：wfl 新增 `hour()` 函数（需 wp-reactor 发布 tag + warp-fusion
bump）替代 strftime 的 chrono 格式化，预期收益有限（A/B 已证 strftime 非主导）。

**跨规模对比（2026-08-25，Mac 同机 10M/30M/100M，q14）**：

| 规模 | EPS | RSS_peak (MB) | CPU avg/max (%) | evict | load |
|---|---|---|---|---|---|
| 10M | 7,201,949 | 2,606 | 410 / 751 | 0 | 2.9 |
| 30M | 7,250,304 | 3,865 | 547 / 731 | 468 | 4.1 |
| 100M | 5,994,744 | 4,248 | 616 / 737 | 2,272 | 5.8 |

- **速度与规模无关**：10M/30M 几乎重合（7.20 vs 7.25M）；100M 的 6.0M 是负载差异
  （load 5.8 vs 2.9/4.1），非规模退化——q14 无状态，sentinel 测的是稳态消化速率。
  参照：Linux 10M 5.36M / 30M 5.49M 同样持平。
- **内存亚线性、30M 后饱和**：1m≈1.4GB → 10M 2.6GB → 30M 3.9GB → 100M 4.2GB
  （30M→100M 仅 +0.38GB）。RSS 大头是 parse 缓冲 + 瞬时积压 + 帧 ingest，随消费
  速度饱和，不随数据量线性涨——无窗口状态的查询画像。
- **CPU avg 随规模上升**（410→547→616%）：10M 活跃窗仅 ~1.4s 样本少、启动占比高；
  长窗下稳态多核占用被充分采样。max 稳定 ~730-750%（10 核 Mac 上限）。
- **evict 正比于数据量**（0 → 468 → 2,272）：内存预算驱逐次数随处理量线性涨（预期）。
- 对比 q19（10M→30M 0.33× 规模退化）：q14 无此类退化，100M 与 30M 速度/内存持平。

**工具修复（2026-08-25，wfgen `cmd_perf_diag`）**：原实现 `std::fs::read` 整文件读入
+ 复制一份载荷——30M 帧 6.4GB×2 在 16GB 机器上 tcp send 失败（daemon 侧 0 字节 EOF），
1m/10m 正常。已改**流式发送**（`send_payload_stream`：文件前缀 `[0, end)` 直接
`tokio::io::copy` 到 socket + 哨兵帧，零内存驻留；`prefix_for_n` → `prefix_range_for_n`
返回字节区间）；30m diag 已在本机跑通（q14 30M 墙表见上，floor 305.6ns/rules+59.1/full+70.4）。
注：大 N 墙梯 EPS 受「每档重发整个文件」的发送耗时主导（floor 30M 仅 3.27M EPS），
归属结构以 1m 档为准。

**改进路径（2026-08-25 复盘）**——30M 墙表解读：floor 305.6ns 是**发送耗时**
（客户端 6.4GB 文件 copy，非引擎；引擎自身 floor 见 1m 墙表 50.8ns）；可改进的引擎成本
集中在两档**增量**：rules +42~59ns（bind filter 全量逐行求值）、full +54~70ns（输出链）。

| 优先级 | 目标段 | 方向 | 性质 |
|---|---|---|---|
| ① | full（输出链） | **列式 cell 求值**：fmt/strftime/count_char 逐行调用 → 向量化（L3 批量列 push 已生效，但 cell 求值仍行式） | wp-reactor 引擎级，惠及全部字符串重查询（q14/q22/q10/q12） |
| ② | rules（bind filter） | **列式 bind 过滤**（向量化）；规则侧折叠 `0.908*price` 边界有浮点语义风险，不建议 | wp-reactor 引擎级 |
| ③ | — | 规则侧已探尽：strftime `let` A/B 零增益、`hour()` 收益有限 | 不做 |

> 结论：q14 的 vs VVR 差距本质是**引擎行式 cell 求值**成本，非查询写法问题。
> 改进必须进 wp-reactor 做列式字符串/过滤求值（通用能力，建议独立立项），不要为 q14 单点投入。
