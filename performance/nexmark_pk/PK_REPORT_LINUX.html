对等分析（硬件与 VVR 8 CU 同量级）

  1. 4/7 领先 VVR：复杂窗口（Q4/Q5/Q7，3.7-4.4×）与 join（Q9，8.6×）是对等硬件下的架构优势区——单进程内存引擎 vs 分布式算子链（KeyBy 重排 + 序列化 + state + checkpoint），复杂查询的分布式代价放大仍是主因；
  2. 简单查询（Q1/Q2/Q3）落后 VVR（0.46-0.81×）：VVR 对简单过滤/投影/轻 join 的优化占优——Mac 的“7/7 全胜”含 16 核 M3 Max 硬件红利，不可作为对等结论；
  3. vs Mac 约 1/3（0.29-0.47×）：8 核 vs 16 核 + 云 CPU 单核弱；RSS 同步下降（吞吐低 → 驻留少）；
  4. 每核效率（EPS ÷ CPU 均核数）：q1 与 Mac 相当（755k vs 799k/核，核数主导）；q2 0.58×、q5/q7 0.61-0.65×；join（q3/q9）0.22-0.26× 差距最大——join 内存带宽敏感，云 CPU 带宽弱放大差距。

结论

  • 对等硬件（8 CU）下 wfusion 复杂窗口与 join 仍显著领先 VVR（3.7-8.6×），简单查询落后（0.46-0.81×）——优势区与 Mac 报告一致但幅度收敛，简单查询需引擎优化（规则输出列式化、简单投影路径减成本）才能对等反超；
  • 吞吐约为 Mac 的 1/3：8 核 vs 16 核 + 云 CPU 单核弱；每核效率 q1 相当，join 带宽敏感差距最大；
  • 对外引用建议：涉及与 VVR/OSS 的公平对比使用本报告（8 CU 对等）；Mac 报告（7/7 全胜）作为硬件上限参考，两者口径分开引用。

诚实边界

  1. 环境已记录（2026-08-17 补录）：AMD EPYC 9T95 KVM 虚拟机，8 vCPU / 8 核，30GiB 内存，Ubuntu 24.04.4（内核 6.8.0-137）；vs Mac M3 Max 的差距含 EPYC 单核（~2.4GHz 量级）与 M3 性能核的频率/带宽差；
  2. 查询/数据近似与 Mac 报告一致：Q4 为 bid⋈auction join 近似（非 category 均价）、Q5/Q7 阈值版；
  3. Flink 数字来源单一（白皮书，不可复现）；OSS 为 12 vCPU（比本次 8 CU 更多），vs OSS 倍率含核数差异；
  4. sink 为 blackhole（discarding 口径），落盘 file sink 慢 ~4-5%。
