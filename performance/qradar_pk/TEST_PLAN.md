# qradar_pk 性能测试方案（TEST PLAN）

> 目标：让本场景的吞吐/内存数字**可复现、可追溯、有人认同**——数据形态符合真实 SIEM 部署、
> 规则对标 QRadar EP 认证、测量口径诚实透明。
> 配套：`README.md`（实测结果与行业定位）、`PK_REPORT_MAC.md` / `PK_REPORT_LINUX.md`（对外报告）。
> 本文档是**先于实测的测试方案**：先讲清楚"要测什么、为什么这样测、怎么测才可信"。

## 1. 测试目标与信度模型

### 1.1 要回答的问题

本场景不是一个"跑个数字"的黑盒——它要对以下问题给出经得起推敲的回答：

| # | 问题 | 意义 |
|---|---|---|
| 1 | **450 条有状态规则下，引擎的真实持续吞吐是多少？** | 对标 QRadar EP 认证（80k @ 451），给客户一个可比的量级 |
| 2 | **在现实数据形态（海量源 IP、突发流量、稀疏异常）下，吞吐/内存如何扩展？** | 真实 SIEM 负载，而非玩具数据 |
| 3 | **窗口内存是否始终有界？是否丢数据？** | #18 门禁：`memory_evicted=0`、无驱逐风暴 |
| 4 | **测量口径是否诚实？数字能否复现？** | 公信力核心：同输入同负载同结果 |

### 1.2 信度模型（为什么这个测法可信）

可信度来自四层，缺一不可：

1. **数据符合现实**：源 IP 长尾、事件时间非均匀、异常稀疏——不是均匀玩具流。
2. **规则对标认证**：450 条 vs QRadar 认证 451 条，规则类别覆盖引擎全部路径。
3. **口径诚实**：明说 EPS 是"引擎消化"还是"注入速率"，不拿被限速/被背压的数字冒充峰值。
4. **可复现**：确定性 seed（42）、固定事件量（200K，可调）、同负载块测量。

## 2. 数据形态设计（符合现实）

> `scripts/gen_events.py` 产出，seed=42 确定性可复现。

### 2.1 源 IP 键：重尾（长尾基数）

| 段 | 数量 | 角色 | 说明 |
|---|---|---|---|
| `10.60.x.y` | **60** | **固定攻击源** | 异常流量（denied / syn / login_fail / 大 dns）集中于这一小撮源 |
| `10.1.x.y` | **40** | 热点正常源 | 高频但在正常情况下 |
| `10.0.x.y` | **10000** | 长尾正常源 | 大量低频正常 IP，模拟"主要合法 + 罕见异常" |

- **唯一源 IP 总数 ~10100**，对齐 QRadar 认证 250k 唯一源 IP 的方向（受 200K 事件量约束取 1 万量级）。
- **异常集中于攻击段**：conn denied/syn ~84% 来自 `10.60.*`，auth failed 同理——制造"异常稀疏但确定触发"的现实形态。
- 正常源承载 ~70% conn 流量（映射 allowed），攻击源 ~30%（映射 denied/syn）。

**为什么这样设计**：真实 SIEM 是"大量正常 IP 低频 + 少数攻击 IP 集中"。旧版 1000 均匀池让每个 IP 事件数均等、告警每刻触发（几百万 emitted），既不现实又测不到真实实例基数压力。

### 2.2 事件时间：泊松到达 + 热点时段（非均匀）

- 事件时间用**指数分布间隔**（泊松到达）+ **周期热点时段**，总跨度 **~12min**（3+ 个 `over=2m` 窗口周期）。
- 实测事件间隔：最小 ~121µs / 中位 ~2105µs / 最大 ~36ms——**非均匀**，含瞬时热点与长尾。
- `_timestamp` 随之生成，`event_time` 驱动窗口老化。

**为什么**：旧版 300µs 均匀线性让事件时间涨速与窗口 over 匹配，但忽略了"真实流量有突发热点"。非均匀时间让窗口**在热点瞬时吃满、平时有界**，是对窗口边界的真实压力测试，而非恒稳。

### 2.3 告警语义：稀疏异常

- 通过攻击源集中 + 正常源分散，让**少量异常源触发高频规则**、大量正常源不触发。
- 目标 emitted 从旧版几百万 → **几十万量级**（稀疏化），贴近现实"告警=罕见异常"。

### 2.4 事件源占比（不变，覆盖引擎路径）

conn 50% / firewall 15% / proxy 10% / auth 10% / dns 10% / file 5%，覆盖
ip/digit/float/bool/chars/array/object/hex 富类型 + chars 实体。

## 3. 注入方式与测量口径（诚实）

> `run.sh` 从 `wfgen send`（JSONL 实时编码，~200k/s 客户端墙）切到
> **`wfgen send-arrow`**（预编码 frames raw-copy）。

### 3.1 为什么切 send-arrow

| 注入 | 客户端编码墙 | 引擎能测到的上限 |
|---|---|---|
| `wfgen send`（JSONL） | **~200k/s**（逐行 parse+编码） | 测不到 >200k 的引擎能力 |
| `send-arrow`（预编码 raw-copy） | 无（纯字节回放） | 引擎真实能力 |

send-arrow 是**唯一能绕过客户端编码墙、测到引擎真实处理能力的注入方式**。

### 3.2 限速注入（`--rate-bytes`，持续注入的基础）

- send-arrow 原生是 **raw-copy 全速回放**（瞬时 burst）。**burst 已被禁用**（§3.4）——它会把事件瞬间塞进窗口造成积压、测不出持续能力。
- 持续注入用新增的 **`--rate-bytes <bytes/s>`**（默认 0 = 不限速，不影响 nexmark）：按目标字节速率**匀速喂**，保持 raw-copy 零解码。
- 注入速率 ↔ EPS 换算：`RATE_BYTES ≈ 目标EPS × 每事件字节数`（实测 ~240-244B/事件，150k EPS ≈ 36.6 MB/s）。

### 3.3 两种口径，必须明说测的是哪个

| 口径 | 含义 | 用途 |
|---|---|---|
| **注入限速**（EPS = 目标注入速率） | 引擎能不能在这个匀速注入下跟上（无积压、emitted 平缓） | 持续负载稳定性 |
| **引擎消化**（EPS = N / 引擎处理完墙钟） | 引擎把 N 事件全部处理完的耗时 | 引擎实际能力上界 |

**诚实框架**：分档扫描注入速率（如 60/80/100/120k EPS），找到**引擎能平稳跟上的最大注入速率**（拐点）——这才是"持续能力"的公信力数字；高于拐点的注入速率会导致积压/退化，应在报告中标为"超过持续能力"而非峰值。

### 3.4 持续注入测速（唯一有效法，2026-08-19 实证）

> ⚠️ **测速只能用「持续注入」**，禁用 burst（一次性把 N 全灌进引擎）。
> burst 会把事件瞬间塞进窗口，造成**窗口积压**——N 越大积压越重，digest 越失真
> （500 万 burst 450 规则只剩 44K，而持续注入下引擎能到 ~150K）。
> **持续注入 = send-arrow 限速匀速喂**，引擎边收边处理、窗口正常老化，才能测真实持续能力。

**测法**：`send-arrow --rate-bytes R` 匀速喂 N 个事件，分离两个墙钟：

| 信号 | 含义 |
|---|---|
| **注入墙钟** | 推完 N 事件的时间（≈ N / 注入速率） |
| **全墙钟** | 注入开始 → emitted 停滞（引擎消化完） |

**判定**：`全墙钟 / 注入墙钟 ≈ 1` → 引擎跟上（消化 ≥ 注入速率）；`>> 1` → 跟不上（消化 < 注入速率）。
**逐步提高注入速率 R，找到「引擎能稳定跟上」的最高 R = 持续能力拐点**。

**实测（450 规则，单 IP，300 万 N，load 高干扰下供趋势参考）**：

| 注入速率 | 注入墙钟 | 全墙钟 | 比值 | 引擎消化 |
|---|---|---|---|---|
| 150K EPS | 23.1s | 26.7s | **1.15** | ~115K |
| 300K EPS | 23.4s* | 29.0s | 1.24 | ~103K |

*（300K 注入墙钟应 ~10s，被高 load（14）拖慢——load 低时注入才准）

**结论（趋势）**：持续注入下 450 规则引擎消化 **~110-150K**，能稳定跟上 150K 注入。
**clean load 下应更高，需在好窗口重测拐点**（§4.2）。

## 4. 测试用例矩阵

> 事件量默认 **300 万**（`./run.sh 3000000`），注入方式一律 **send-arrow `--rate-bytes` 持续注入**（见 §3.4）。
> N 要够大让注入持续数秒（进入稳态），但不能大到单次注入拖垮窗口（持续注入下引擎边收边消化，
> 不像 burst 会积压）。可调（`./run.sh <N>`）。

### 4.1 正确性 / 回归门禁（每场合跑，金标准）

| 用例 | 动作 | 验收 |
|---|---|---|
| **#18 驱逐门禁** | 跑任意 N，检查驱逐 | `memory_evicted=0`（wfusion.log 无 "in memory eviction"）|
| **告警发射** | 检查 metrics emitted | `emitted_total` ≥ 10000，且各规则类别有命中 |
| **无丢/无late** | 检查 metrics | `dropped_late=0`、`cursor_gap=0`、`serialize_failed=0` |

### 4.2 吞吐测量矩阵（持续注入，N=300 万）

> 方法见 §3.4：send-arrow `--rate-bytes` 匀速喂，用「全墙钟/注入墙钟 ≈1」判定引擎跟上。
> 逐步提高注入速率找拐点 = 持续能力。**禁止 burst**。

| 用例 | CONNECTIONS | RATE_BYTES | 目的 |
|---|---|---|---|
| **注入速率扫描** | 1 | 150K/300K/500K… EPS 对应字节 | 找「引擎能稳定跟上」的拐点（持续能力） |
| **拐点复核** | 1 | 拐点附近 × 2 档 | 确认拐点稳定（同 load 重测） |
| **多连接持续注入** | 4（分片键闭包） | 拐点附近 | 验证持续能力是否随并发提升 |
| **规则数二分** | 1 | 持续注入 | 规则量墙定位（450→225→112→…→3，各档找拐点） |

### 4.3 内存 / 扩展探针

| 用例 | 目的 | 验收 |
|---|---|---|
| N=200K | 基线 RSS / 窗口内存 | RSS 平台期稳定、无驱逐 |
| N 翻倍（400K） | 内存是否有界 | 事件时间跨度固定（12min），窗口内容 ≈ over×速率而非 ∝ N |
| qradar 3M/10M（大 N） | 任意 N 不卡死 / 不驱逐 | 依赖窗口背压修复（见下文遗留） |

### 4.4 公平对标

- 同数据、同 N 下，对比**当前 wfusion** vs **QRadar 认证方法论数字**（80k @ 451）。
- 用**每核效率**（EPS/核心）消除硬件规模差异（PK_REPORT 已用）。
- **诚实边界明说**：硬件不对等（M3 笔记本 vs QRadar 服务器）、键基数（10100 vs 250k）等——不夸大倍率。

## 5. 环境与复现

- **二进制**：`warp-fusion/target/release/wfusion`（bench.sh 优先本地构建），需 `cargo build --release --bin wfusion` 后复制/确认 hash。
- **数据**：`gen_events.py <N>`，seed=42 确定性，同输入可复现。
- **帧预编码**：`wfgen dump-frames`（同 daemon 内），`send-arrow` 回放同一 daemon（schema 一致性是 send-arrow 可用的前提）。
- **负载纪律**：本机常载（loadavg 波动），A/B 必须**同 load 块配对**；EPS 读数带 load 噪声。
- **计时信号**：qradar 无 `append_total`（nexmark 用），引擎消化完成用 **emitted_total 累计停滞** 判定。

## 6. 验收标准（一个测试方案是否可信的关键）

这份测试方案 + 实测报告若能回答以下问题，才具备公信力：

1. **数据可复现吗？** → seed=42 + 固定 N → 是。
2. **EPS 是引擎能力吗？** → 明说注入限速 vs 引擎消化，不混淆 → 是。
3. **异常稀疏吗？** → emitted 从几百万降到几十万，贴合现实 → 是。
4. **窗口有界且不丢吗？** → #18 门禁（驱逐=0、无 dropped_late/无 gap）→ 是。
5. **与认证可比吗？** → 450 vs 451、每核效率、诚实边界 → 是。
6. **数字用的是持续注入口径吗？** → 只用 send-arrow `--rate-bytes` 匀速喂 + 拐点扫描，**无 burst** → 是。

## 7. 遗留与已知边界（诚实）

1. **窗口背压修复未落地**（`issues/window-overload-drop-vs-backpressure.md`）：大 N（10M+）瞬时注入时窗口满会**丢批**而非反压。200K 稳态下事件时间跨度 12min ≫ over=2m，窗口能自然老化，不触发；但**任意大 N** 需先修窗口背压。
2. **send-arrow 限速是字节级节流**，非事件级——换算 EPS 依赖"每事件字节数"（实测 ~244B，随数据形态漂移，需每轮实测确认）。
3. **sharded 透传路径未严格限速**（`send_arrow_sharded` 接受 `rate_bytes` 参数但暂不节流）——分片注入 + 限速组合需后续实现，当前侧重单连接/多连接 raw-copy 路径。
4. **计时信号** `emitted_total` 累计停滞有 <1s 延迟（exporter 1s 落盘），短跑（<1s）有 ± 误差；N=200K 下误差占比小，可信。
