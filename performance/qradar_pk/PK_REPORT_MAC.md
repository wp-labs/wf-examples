# wfusion vs IBM QRadar EP — 450 规则高压吞吐性能报告（Apple Silicon 环境）

> 测试日期：2026-08-17（P0-② content 记账 2GB 之后，当前二进制）
> 对标：IBM QRadar Event Processor 认证负载（**80k EPS @ 451 条规则**）
> 场景：`wf-examples/performance/qradar_pk`（450 条有状态规则 / 6 类事件源 / 1000 sip 键）

---

## 1. 摘要

单台 **Apple M3 Max（16 核 / 64GB）** 上，wfusion 以 **450 条有状态规则** 处理 100 万事件
长稳测试：**稳态 EPS 150-162k、RSS ~6.7GB、内存驱逐 0、emitted 1000 万+ 条**。

| 结论 | 结果 |
|---|---|
| 450 规则稳态吞吐 | **150-162k EPS**（三轮 150.4 / 156.0 / 162.4k，±8% 相位波动） |
| vs QRadar EP 认证上限 | **1.9-2.0×**（80k @ 451 规则） |
| 每核效率 | **17-27k EPS/核**（vs QRadar 虚拟版 ~1.0-1.4k，**高 12-27×**） |
| 内存 | RSS ~6.7GB / 64GB（10%），驱逐 0，#18 门禁通过 |
| 正确性 | emitted 10.2-10.4M，371/450 规则触发（其余阈值/过滤不满足，正常） |

## 3. 引擎配置与调参（nexmark 经验应用）

| 参数 | 值 | 依据 |
|---|---|---|
| `parse_buffer_bytes` | **2GB**（content 记账） | nexmark P0-② 甜点；qradar 供给充足非瓶颈 |
| `parse_parallelism` / `rule_parallelism` | 10 / 10 | nexmark 调优值 |
| `instances`（W-RDP） | 4 | nexmark 经验（单连接下不生效，多连接才有效） |
| conn_events `max_window_bytes` | **4GB**（原 1GB） | 1M 长跑下窗口深内容 ~2.5GB+，1GB 触发 38 条有损驱逐；4GB 后驱逐 0（nexmark 窗口 cap 与数据量匹配经验） |
| `max_total_bytes` | 8GB（原 2GB） | 同上 |
| CHUNK（批） | **10000** 最优 | 162.4 vs 156.0k @ 100000——qradar 规则求值主导，批大小非杠杆 |

## 4. 测试结果（100 万事件，blackhole sink）

### 4.1 参数矩阵

| 配置 | EPS | RSS 峰值 | 驱逐 | 说明 |
|---|---|---|---|---|
| 基线 200k / CHUNK=10000（窗口 1GB） | 147.6k | 2.25GB | 0 ✅ | 当前二进制即高于旧记录（96.7k） |
| **1M / CHUNK=10000（窗口 4GB）** | **150-162k** | **~6.7GB** | **0 ✅** | **稳态口径（三轮 150.4/156.0/162.4k）** |
| 1M / CHUNK=100000（窗口 4GB） | 156.0k | 6.55GB | 0 ✅ | 大帧略降 |

### 4.2 正确性侧证

- **emitted 10.2-10.4M**（100 万事件 → 1000 万+ 告警，含多规则命中）
- **371/450 规则触发**（200k 时 293 条；其余规则阈值/过滤条件在该数据分布下不满足）
- 驱逐 0、无 dropped_late / serialize_failed / cursor_gap
- #18 门禁（object 大批次不被窗口内存驱逐）通过

### 4.3 关键结论

1. **450 规则稳态 150-162k = QRadar EP 认证上限（80k）的 ~2×**，且是带窗口/实例的
   有状态关联规则，不是裸过滤；
2. **窗口 1GB 是 1M 长跑的坑**：conn 窗口深内容 ~2.5GB+（200k 的 5×），1GB 触发
   有损驱逐；**4GB 后驱逐 0**——窗口 cap 必须与数据量匹配（nexmark 同经验）；
3. **供给非瓶颈**：EPS 远低于引擎输入能力（nexmark q1 单规则 7.5M），450 规则求值
   是瓶颈；连接数/分片/instances 非杠杆（单连接 1M 已测稳态，README 旧记录双连接
   仅 +3%）；
4. **CHUNK=10000 最优**：与 nexmark 100k 帧甜点不同，规则求值主导时批大小影响小。

## 5. 行业定位（450 规则，单节点 M3 Max）

换算：~156k 事件/s × 450 规则 ≈ **7000 万次规则求值/s**（每核 ~17-27M 次/s，
均摊 ~37-60ns/规则求值，含 per-sip 实例状态与窗口维护）。

| 参照 | 吞吐 | 规则数 | 硬件算力 | 说明 |
|---|---|---|---|---|
| QRadar EP 1699（虚拟版） | 80k EPS（认证上限） | 451 | 56-80 核 + 128GB | 事件均值 382B，250k 唯一源 IP；含板载采集/规范化 + 2TB 存储 |
| QRadar 物理 appliance（1605） | 20k EPS（许可上限） | 同上 | 16-20 核 + 64GB | 双冗余电源 1U 机架 |
| **wfusion（本场景）** | **150-162k EPS** | **450** | **单进程 @ M3 Max，有效并行 6-9 核，RSS 6.7GB** | 1000 sip 键基数 |

**每核效率**：QRadar 虚拟版 ~1.0-1.4k EPS/核（80k÷56-80 核）、物理版 ~1.0k EPS/核；
wfusion 在 6-9 核跑 150-162k → **17-27k EPS/核——高约 12-27×**。

---

## 6. 诚实边界

1. **硬件不对等**：wfusion 单进程 @ M3 Max 笔记本芯片 vs QRadar 56-80 核 + 128GB
   服务器——倍率含硬件口径差异，但每核效率对比（12-27×）已消除规模因素；
2. **键基数不对等**：本场景 1000 sip 复用 vs QRadar 250k 唯一源 IP——直接对比偏保守
   有利于 QRadar（键基数大 → 实例状态/哈希成本更高）；
3. **EPS 口径**：send 墙钟（客户端回放完成时刻）——1M 稳态三轮稳定（±8%），
   且注入速度 ≈ EPS（背压约束），未用预编码帧（send-arrow）做客户端成本隔离；
4. **sink 为 blackhole**（discarding，对齐 Flink Nexmark 口径），落盘 file sink 慢 ~4-5%；
5. **QRadar 数字来源单一**（IBM 官方认证方法论），不可复现；对照含板载采集/存储等
   产品层组件（非仅规则引擎），利于 QRadar。
