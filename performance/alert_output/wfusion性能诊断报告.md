# WFusion 性能瓶颈与调优方案（极简版）

> 日期：2026-09-09；状态：问题已定位，正式源码和规则尚未修改

## 结论

主瓶颈在 `emit`：规则命中后构建输出记录太慢。

| 阶段增量 | 成本占比 | 判断 |
|---|---:|---|
| `floor -> rules`：`+340.7 ns/事件` | 约 21% | 规则求值，有成本但不是主墙 |
| `rules -> emit`：`+1022.1 ns/事件` | 约 64% | 输出构建，主墙 |
| `emit -> full`：约 `+1.3 ns/事件` | 接近 0% | BlackHole 不是当前主墙 |

三轮结果方向一致。CPU 约使用 10 核总量的 40%，计数器正常，因此不是简单的 CPU 打满或接收不足。

本结论只适用于：3M 事件、`rule_shards=4`、BlackHole、单轮墙梯；不等于 File/Doris 生产吞吐。

## 为什么慢

当前 WFL 输出中有：

- `sha256`、`sha1`；
- 多次字符串拼接；
- 嵌套字段访问；
- `coalesce` 和多层 severity 判断。

这些表达式没有全部支持 WFusion 的列式快速路径。只要一个输出字段不支持列式处理，整段输出就会回退到逐事件创建对象和写字段，导致 `emit` 变慢。

## 已有证据

- 去掉两个哈希后，`emit` 成本约下降 29%；但会改变 ID，不能直接上线。
- 只输出少量简单字段时，`emit` 成本降到约 `133.6 ns/事件`；说明输出构建是主要成本。
- 用 `let` 提取公共表达式没有稳定收益；它主要是编译期内联，不是运行时缓存。
- `entity`、`on each`、`score` 不能简单删除，否则规则解析失败或改变业务语义。

## 推荐方案

### 1. 首选：优化 WFusion 引擎源码

不是先重写业务 WFL，而是让引擎支持当前输出的列式或混合列式执行：

- 批量支持 `sha1/sha256`、字符串拼接、`coalesce`；
- 支持或提前展开嵌套字段；
- 简单字段走列式，复杂字段逐行计算，避免整段回退；
- 保证 ID、null、缺失字段和 severity 语义完全不变。

### 2. 不改引擎时：只做 WFL/输入减负

- 上游将嵌套字段展开为平铺字段；
- 删除确认不需要的输出字段；
- 只有业务确认兼容后，才能减少或替换哈希。

这只能局部提速，不能替代引擎列式优化。

### 3. 参数暂不作为重点

保持 `rule_shards=4`。暂时不要靠扩大窗口、增加 shard 或提高 sink 并行度解决问题，除非出现 eviction、channel full 或 backlog 持续增长。

## 下一步

1. 固定当前 WFL，保存输出字段和 ID 对拍基线。
2. 在 WFusion 引擎中实现列式/混合列式输出。
3. 重新构建 release，并重复 3 次：

```bash
cd performance/wfusion_new
./diag.sh 3m --sink blackhole --stages floor,rules,emit,full --rule-shards 4
```

4. 重点比较 `rules -> emit` 增量；确认输出完全一致后，再测试 File/Doris sink。

## 合入标准

- 输入、接收、处理、输出计数完整一致；
- 所有输出字段及两个 ID 逐字段一致；
- 无错误、丢数、eviction、channel full；
- 三轮测试中 `emit` 增量稳定下降；
- File/Doris sink 仍能正确落地。
